EDRMS Utilization Report · KPI work order

Total Documents in EDRMS

This number does not exist in any system today. Not in the reporting database, not in any Microsoft report, not in AvePoint. Producing it needs one new job from the development team and two answers from the client. Here is exactly what each side has to do.

14 August 2026 S/N 2 · PPT s15, s34, s40 Test tenant 7rkd12

Why there is no number to look up

The EDRMS is not a separate application. It is app {B255A2AF-7F63-4A30-966A-5D5FD99F97D7} installed into SharePoint sites, which is what puts the Declare as Record button on a library.

The reporting database table public."Records" holds about 1,990 rows in UAT, and every one is a declared record. There is no row for a document that was never declared. The database does not know those documents exist.

So today the bank can answer "how many records were declared". It cannot answer "how many documents are there", and therefore cannot answer any question shaped as a percentage, because every one of those needs this number underneath it.

Do not use the usage report as a substitute

The SharePoint site usage export has a File Count column summing to 32,833. It is not this number and must not be presented as it. It counts every site in the tenant rather than EDRMS sites, it counts system libraries, and it counts non business libraries. It is an upper bound with no way to narrow it.

The pipeline, and who owns each step

Five steps, in order. Steps 1 and 3 are settled and proven against the tenant. Step 2 is the blocker. Steps 4 and 5 are ordinary development work.

1 Dev

Enumerate every site in the tenant

A document lives in a library, a library lives in a site. Everything starts from a complete site list.

Do not use GET /sites?search=*. It looks like an enumeration and is not one: it is served from the search index and returns only what has been crawled. Measured on 14 August 2026 it returned 451 sites against 1,676 from Get-PnPTenantSite. A scan built on it would silently miss most of the tenant and report a confidently wrong total.

Get-PnPTenantSite # 1,676 sites GET /sites?search=* # 451 sites, incomplete

Enumerate through the SharePoint admin API, then use Graph for everything below the site.

2 Blocked

Keep only the EDRMS compliant sites

The rule is known and is not in dispute: a site is compliant when the EDRMS app is installed on it. Site Contents shows the installed app as its own row in a browser, and its Modified date differs between sites, so it is not a bulk stamp.

What nobody has answered is which API returns that app list across every site at once. Checking one site in a browser is not the same thing as filtering 1,676.

This is the single question standing between the bank and this KPI. Everything else is built.

3 Proven

Walk each library and count only files

For each compliant site, list its libraries, then walk each library's items. Two rules decide whether the resulting number is right, and both were verified against a real library on 14 August 2026.

An item with a folder facet is a folder. An item with a file facet is a document. Count only files.

A folder's size is cumulative, meaning it already contains everything beneath it. Summing size across all items counts the same bytes at every level of the tree.

Measured on one libraryCounting rowsChecking facets
Documents7354
Storage684.3 MB172.2 MB

Getting it wrong overstates the document count by 35 percent and the storage by roughly four times, and nothing in the output looks wrong.

Two further rules, both from the same measurement. Exclude system libraries, which exist on every site and hold no business document: Apps for SharePoint and Client Side Assets among them. And address libraries by id, never by name, because library names in this tenant contain commas, quotes and backslashes.

4 Dev

Write one row per document, keeping the join key

The scan writes to rpt.utilization_report in the reporting database, one row per document, projected at about 3.47 million rows. That table is replaced each week rather than appended to.

Every row must carry ListId and ItemId. That pair is the grain public."Records" uses to identify a document, and it is the only thing that makes step 5 possible.

The ListId is not on the drive object. The /drives response carries driveType, owner and quota and no list block, so reading drive.list.id yields null on every row. The scan completes, the output looks plausible, and the join matches nothing. Fetch it explicitly:

GET /drives/{driveId}/list?$select=id

Load into a staging table and swap, so the report never reads a half written table. Nothing pushes into the database: a job pulls on a schedule, weekly. Microsoft and AvePoint cannot write to PostgreSQL.

5 Dev

Join scanned against declared

Once the table exists, one query produces the figure the whole report has been waiting for.

LEFT JOIN rpt.utilization_report ON ListId + ItemId AGAINST public."Records" matched = declared unmatched = never declared

Total Documents in EDRMS is the row count. The declaration rate is the matched proportion. Neither can be produced any other way, which is why this scan sits on the critical path rather than being an optimisation.

What to give the development team

Read only work throughout. The job needs Graph permission Sites.Read.All, which is a straightforward approval, plus read access to the reporting database.

  1. Answer the compliance question first. Which API returns the installed app list across all sites, so the scan can filter to EDRMS sites rather than scanning the whole tenant. Nothing else is blocked; this is.
  2. Replace site enumeration with the admin API. search=* returns 451 of 1,676 sites. Confirm the true count in production before the first full run.
  3. Create rpt.utilization_report to the agreed 73 column design, in the rpt schema alongside public, so a query can join across the two.
  4. Build the weekly job implementing steps 1 to 4. A working simulation already exists and produces a CSV rather than inserting, so the logic can be compared row for row before anything writes.
  5. Use delta tokens for the refresh. Each library's @odata.deltaLink returns only what changed since the last run, which is what keeps a weekly job at minutes rather than hours after the first pass.
  6. Add a DisposalStatus field to the EDRMS application. Separate from this KPI, but it is the same development conversation. Nothing currently records whether a disposal happened, so the disposal screens cannot be built at all.

What to get from the client

Two of these block the number itself. The third and fourth block the breakdowns beneath it, which is what anyone will ask for within a minute of seeing the total.

1. Which sites are EDRMS sites?

Until the app detection question is answered, supply a maintained list of compliant site URLs. Even twenty sites gives a real, defensible number for those twenty and proves the whole chain end to end.

Without it the scan covers the entire tenant and the result is an upper bound, not Total Documents in EDRMS. The figure of 1,057 compliant sites currently circulating is a placeholder inherited from an early prototype and has never been measured.

2. What counts as a document?

The scan counts every file. That includes notification emails the EDRMS application saves back into libraries as .eml, and it includes duplicates: one library was measured holding eight byte identical copies of the same PDF.

No filter is proposed, because a rule dropping .eml would also drop genuinely declared correspondence. The client should decide, and the decision should be recorded, because it changes the headline number and someone will ask.

3. The site to department list, from RAC

One row per site, giving the owning department and division. Roughly a thousand rows, supplied once.

Department is attached to the site, not the document, and documents inherit it. Confirmed feasible by development on 10 August with no migration required. Twenty nine of the 123 logged requirements wait only on this list, along with the entire Department Insights dashboard.

4. Confirm the department assumption

Is it acceptable that every document in a departmental site counts to that department, regardless of who created it?

Every departmental breakdown in the report assumes yes. If the answer is no, the design changes rather than the report, and it is far cheaper to hear that now.
