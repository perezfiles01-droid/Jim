EDRMS Utilization Report
Asian Development Bank · Reporting Data Design
A proposed reporting layer for the Utilization Report, mapped against the existing EDRMS declaration database (Database Design 12.03). It sets out what the current design already supplies, what is missing, and the tables needed to serve every figure the dashboards show.

1The core problem this design solves

The existing database is an operational system. It records declarations: jobs, queues, attempts, and the resulting records. It is well suited to that, and the Utilization Report should reuse it rather than duplicate it.

But most of the report is about the denominator, not the numerator. Total documents held (3.47M in the prototype), declaration rate per library, storage consumed by format, sites created by department. A declaration log never sees any of that, because a document that was never declared produces no row anywhere in it.

So the reporting layer needs a second source: a periodic scan of SharePoint that counts and measures everything, declared or not. That scan is the single most important addition proposed here, and it is what makes the declaration rate, the storage figures, and the library adoption panels possible at all.

Design consequence. Two grains, deliberately. Declared records are stored one row per record, because there are only tens of thousands of them and the report drills into individual retention and physical counterpart detail. Everything else is stored as bounded periodic aggregates, because 3.47M documents at row grain would be expensive to refresh weekly and no dashboard figure needs that detail.

4Gaps, ranked by what they block

Each of these prevents at least one figure the prototype currently displays.
SeverityGapEffect and proposed fix
Critical File size is captured nowhere. FileMeta holds FileType, FileCreatedDate and sensitivity, but no size. Blocks every storage figure: storage by format, largest libraries by storage, average file size, and the whole left half of Format and Storage. Add FileSizeBytes to FileMeta and capture it in the inventory scan.
Critical Undeclared documents are invisible. The database only ever holds declared records. Blocks total documents (3.47M), declaration rate, and the library adoption panel. There is no fix inside the declaration database. It requires the new inventory scan feeding fact_library_snapshot.
Critical Site table carries three real columns: SiteUrl, SiteName, ProjectEndDate. Blocks sites created by department, the treemap, and the compliant site count. No site creation date, no department owner, no compliance flag, no storage. See dim_site.
High Library table has no ListId or URL, only name, category, division and unit owner. Library display names repeat across sites, which the prototype already handles by always showing a library with its parent site. Without ListId the library cannot be keyed at all. Add it, and the site foreign key.
High ADBMaster is flat. Rows are TermId, TermTitle, TermValue with no parent link. The term store models divisions as children of departments, verified in the tenant. Flattening it loses that, so department to division drill down cannot be derived. Add ParentTermId, or split into dim_department and dim_division.
High ADBMeta is marked out of scope for Release 2026.1, and ADB Document Owner is empty across the sample tracking data. Every department and division grouping in the report depends on this. It is a release scoping decision rather than a technical gap, and it should be raised as such.
Medium No usage metrics anywhere. Site visits and unique viewers come from M365 rather than this database, but they still need somewhere to land. See fact_site_usage_snapshot.
Medium Nothing is time sliced except declarations. Declaration trends work because each record carries a date. Storage, document counts and adoption cannot be trended at all without periodic snapshots.
Medium Physical Records duplicates the entire Records schema. Two tables with identical columns will drift the first time one is altered. Prefer the existing HasPhysical flag on Records plus a view, unless there is a retention or access reason for the separation.
Medium No refresh audit. The dashboards print a "data as of" line, and the Overview deliberately quotes the oldest refresh across its sources. Nothing currently records when each source was last loaded. See etl_refresh_log.

7Decisions needed before building

  1. Is ADBMeta in scope for a release? It is marked out of scope for 2026.1 and ADB Document Owner is empty across the sample data. Every department and division figure in the report depends on it. This is the single biggest item.
  2. What identifies an EDRMS compliant site? A naming convention, the EDRMS Site Type term, or an AvePoint provisioning flag. It sets dim_site.is_edrms_compliant and therefore the denominator of most of the report.
  3. Where does the site to department mapping come from? AvePoint may already hold it from provisioning. If not, it has to be created, and it is a records decision rather than a technical one.
  4. How often does the inventory scan run, and at what grain? Weekly at library and format grain is proposed. Consider keeping weekly snapshots for thirteen weeks and monthly thereafter, so the table does not grow without bound.
  5. Do all retention labels mark items as records? If some do not, dim_retention_label.marks_as_record does real work and every count must filter on it. If all do, the model simplifies.
  6. Should Physical Records stay a separate table? It duplicates the Records schema in full. Unless there is a retention or access control reason, a flag plus a view avoids the drift.
  7. Which storage definition does the report mean? Site storage from M365 includes version history and the recycle bin, so it will not match the sum of current file sizes, often by a factor of two to five. Both are legitimate, they measure different things, and the dashboard must say which one it shows.
  8. Index the columns the report queries on. Any SharePoint column used by the scan or by filters needs an index once a library passes 5,000 items, and these libraries are far past it.
