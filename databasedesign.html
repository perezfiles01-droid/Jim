EDRMS Utilization Report
Asian Development Bank · Reporting Database Design
A reporting layer for the Utilization Report, designed against the live drm-npr PostgreSQL database. Every figure the dashboards show is traced to the table, column and query that produces it.

1Should the Utilization Report have its own tables

Yes. Specifically a separate schema, rpt, in the same drm-npr database, rather than new tables mixed into public or extra columns bolted onto the existing ones.

Four reasons this is the right shape

  • The operational tables are not yours to change. public."Records" is owned by ADBWebServiceMI1 and managed by Entity Framework migrations, visible as __EFMigrationsHistory. Any column added by hand risks being dropped or renamed by the next vendor release. A separate schema is never touched by those migrations.
  • Reporting wants a different shape. The dashboards need pre joined dimensions, periodic snapshots and aggregates. Those are wrong things to put in a transactional table that the declaration app writes to on every job.
  • Permissions separate cleanly. Power BI gets USAGE on rpt and SELECT on its tables, and nothing at all on public. Today a reporting connection would need read access to the live declaration tables, which is a wider grant than anyone needs.
  • Refreshes become safe. The reporting tables can be truncated and rebuilt, or reloaded incrementally, without any possibility of touching production declaration data. A failed refresh degrades the report and nothing else.
Two deliberate exceptions. Two things genuinely must change inside the application's own tables, because they can only be captured at declaration time and cannot be derived afterwards. Both are in section 3, and both are small.

3The two changes needed inside the application

Everything else can be solved in the reporting layer. These two cannot, because they can only be captured at the moment of declaration.

Critical  File size is not captured

FileMeta currently carries file type, created date and sensitivity label. It does not carry size, and size cannot be recovered later for a document that has since changed or been deleted.

Without it: storage by format, largest libraries by storage, and average file size have no source. That is the entire left half of the Format and Storage dashboard.

-- what FileMeta holds today
{ "FileType": "docx", "FileCreatedDate": "2026-03-11T05:01:03Z",
  "SensitivityLabelName": "Internal", "SensitivityLabelID": "817d4574-..." }

-- what it needs
{ "FileType": "docx", "FileCreatedDate": "2026-03-11T05:01:03Z",
  "SensitivityLabelName": "Internal", "SensitivityLabelID": "817d4574-...",
  "FileSizeBytes": 51224 }

One integer, captured from SharePoint at declaration time. No schema migration is required because FileMeta is already jsonb.

Critical  ADBMeta is empty and out of scope

The workbook marks ADBMeta as out of scope for release 2026.1, and ADB Document Owner is blank across the sample tracking data. It is the department, division and unit of every record.

Without it, every department and division figure in the report is impossible. That is the treemap, the top five departments, the drill down, and the department filters on three dashboards. This is a release scoping decision rather than a technical gap, and it is the single largest open item.

-- ADBMeta, once populated
{ "ADBDepartmentOwner": "CWRD",
  "ADBDivisionOwner":   "AFRM",
  "ADBUnitOwner":       "AFRM-PA",
  "ADBLibraryCategory": "Project Records" }
Values must be the term store codes, and ideally the term GUIDs alongside them, so the reporting layer can join to the hierarchy rather than match on text. The Division term set already nests divisions under departments, so the parent relationship does not need to be invented.

4The rpt schema

Runnable PostgreSQL. Nine dimensions, four facts, one audit table. Nothing here touches public.
CREATE SCHEMA IF NOT EXISTS rpt;

-- ============ DIMENSIONS ============

CREATE TABLE rpt.dim_date (
  date_key        integer PRIMARY KEY,        -- 20260311
  full_date       date NOT NULL,
  year            smallint NOT NULL,
  quarter         smallint NOT NULL,
  month           smallint NOT NULL,
  month_name      text NOT NULL,
  week_of_year    smallint NOT NULL,
  is_month_end    boolean NOT NULL
);

CREATE TABLE rpt.dim_department (
  department_key  serial PRIMARY KEY,
  term_id         uuid UNIQUE,               -- term store GUID
  code            text NOT NULL UNIQUE,        -- CWRD
  name            text NOT NULL,
  is_active       boolean NOT NULL DEFAULT true
);

CREATE TABLE rpt.dim_division (
  division_key    serial PRIMARY KEY,
  term_id         uuid UNIQUE,
  department_key  integer NOT NULL REFERENCES rpt.dim_department,
  code            text NOT NULL,                -- AFRM
  name            text NOT NULL,
  org_unit_type   text,                          -- Division | Resident Mission
  is_active       boolean NOT NULL DEFAULT true,
  UNIQUE (department_key, code)
);

CREATE TABLE rpt.dim_unit (
  unit_key        serial PRIMARY KEY,
  term_id         uuid UNIQUE,
  division_key    integer NOT NULL REFERENCES rpt.dim_division,
  code            text NOT NULL,
  name            text NOT NULL,
  is_active       boolean NOT NULL DEFAULT true
);

CREATE TABLE rpt.dim_site (
  site_key            serial PRIMARY KEY,

  site_name           text NOT NULL,
  site_created_date   date,                     -- from admin centre export
  is_edrms_compliant  boolean NOT NULL DEFAULT false,

  project_end_date    date,

  is_active           boolean NOT NULL DEFAULT true
);

CREATE TABLE rpt.dim_library (
  library_key     serial PRIMARY KEY,
  list_id         uuid NOT NULL UNIQUE,        -- names repeat, this does not
  site_key        integer NOT NULL REFERENCES rpt.dim_site,
  library_name    text NOT NULL,
  library_url     text,
  library_category text,
  division_key    integer REFERENCES rpt.dim_division,
  unit_key        integer REFERENCES rpt.dim_unit,
  is_active       boolean NOT NULL DEFAULT true
);

CREATE TABLE rpt.dim_file_format (
  format_key      serial PRIMARY KEY,

CREATE TABLE rpt.dim_retention_label (
  label_key       serial PRIMARY KEY,
  label_name      text NOT NULL UNIQUE,        -- 10 years after declaration
  duration_years  smallint,
  marks_as_record boolean,                     -- not all labels declare

);

CREATE TABLE rpt.dim_user (
  user_key        serial PRIMARY KEY,
  upn             text NOT NULL UNIQUE,        -- rkyadav.contractor@adb.org
  display_name    text,
  department_key  integer REFERENCES rpt.dim_department
);

-- from public."TrackingRecords", including failures
CREATE TABLE rpt.fact_declaration_attempt (

5Loading fact_record from the live Records table

This is the query that turns declarations into report data. The two gaps from section 3 are visible in it directly.
INSERT INTO rpt.fact_record (
  source_id, document_id, item_id, site_key, library_key,
  department_key, division_key, unit_key,
  declared_date_key, declared_at, declared_by_user_key,
  format_key, file_size_bytes, file_created_date,
  has_physical, physical_justification,
  retention_label_key, retention_applied_at, retention_duration_years,
  due_date_for_disposal, retention_status, sensitivity_label,
  declaration_type, is_deleted, deleted_at)
SELECT
  r."Id",
  r."DocumentId",
  r."ItemId",
  s.site_key,
  l.library_key,
  dep.department_key,                                  -- null until ADBMeta is populated
  div.division_key,                                    -- null until ADBMeta is populated
  u.unit_key,
  to_char(r."CreatedDate", 'YYYYMMDD')::int,       -- CreatedDate IS the declaration date
  r."CreatedDate",
  usr.user_key,
  fmt.format_key,
  (r."FileMeta"->>'FileSizeBytes')::bigint,       -- null until section 3 lands
  (r."FileMeta"->>'FileCreatedDate')::date,
  (r."EDRMSMeta"->>'HasPhysical') IN ('Yes','true','True'),
  r."EDRMSMeta"->>'PhysicalRecordJustification',
  lbl.label_key,
  r."EDRMSRetentionLabelApplied",
  nullif(regexp_replace(r."EDRMSDuration", '\D', '', 'g'), '')::smallint,
  r."EDRMSDueDateForDisposal"::date,
  r."EDRMSMeta"->>'RetentionStatus',
  r."FileMeta"->>'SensitivityLabelName',
  r."DeclarationType",
  r."IsDeleted",
  r."DeletedDate"
FROM public."Records" r
JOIN rpt.dim_site    s   ON s.site_url = r."SiteUrl"
JOIN rpt.dim_library l   ON l.list_id  = r."ListId"        -- uuid, never the name
LEFT JOIN rpt.dim_department dep ON dep.code = r."ADBMeta"->>'ADBDepartmentOwner'
LEFT JOIN rpt.dim_division   div ON div.code = r."ADBMeta"->>'ADBDivisionOwner'
                                    AND div.department_key = dep.department_key
LEFT JOIN rpt.dim_unit       u   ON u.code   = r."ADBMeta"->>'ADBUnitOwner'
LEFT JOIN rpt.dim_user       usr ON usr.upn = lower(r."CreatedBy")
LEFT JOIN rpt.dim_file_format fmt ON fmt.extension = lower(r."FileMeta"->>'FileType')
LEFT JOIN rpt.dim_retention_label lbl ON lbl.label_name = r."EDRMSRetentionLabel"
ON CONFLICT (source_id) DO UPDATE SET
  is_deleted = EXCLUDED.is_deleted,
  deleted_at = EXCLUDED.deleted_at;
Read the three amber lines. They are the whole gap analysis in one place. Department and division resolve to null until ADBMeta is populated, and file size is null until it is captured. Everything else in this query works against the database as it stands today.

6The inventory scan, the one genuinely new pipeline

Nothing in PostgreSQL knows how many documents exist, only how many were declared. This closes that.

A scheduled job walks every EDRMS compliant site through Microsoft Graph, enumerates list items, and writes one aggregated row per library per format. It never stores individual undeclared documents, so the volume stays bounded.

-- pseudocode for the weekly job
for each site in dim_site where is_edrms_compliant:
    for each library in site:
        counts = {}
        for each item in graph.enumerate(library):      -- delta query
            ext = extension_of(item.name)
            counts[ext].documents  += 1
            counts[ext].bytes      += item.size            -- available from Graph
            counts[ext].declared   += 1 if item.isRecord
        upsert into rpt.fact_library_snapshot

-- then record what the dashboards will print as "data as of"
INSERT INTO rpt.etl_refresh_log (source_system, data_as_of, started_at, completed_at, rows_loaded, status)
VALUES ('spo_inventory', now(), :started, now(), :rows, 'success');
Note that file size is available here even though it is missing from Records. Graph returns size on every item. So storage by library and by format can be delivered from the scan alone, and the FileMeta.FileSizeBytes change in section 3 is only needed for per record storage detail. That splits one critical gap into a large half that is already solvable and a small half that needs the app change.

-- Declaration success rate, from TrackingRecords. Arguably the most
-- actionable adoption metric available, and nothing uses it yet.
SELECT d.month_name,
       count(*) FILTER (WHERE a.result = 0) AS successful,
       count(*) FILTER (WHERE a.result = 1) AS skipped,
       count(*) FILTER (WHERE a.result = 2) AS failed,

9Decisions needed before building

  1. Will ADBMeta be populated, and in which release? It is marked out of scope for 2026.1. Every department and division figure depends on it, so this is the largest open item by some distance.
  2. What identifies an EDRMS compliant site? Sets dim_site.is_edrms_compliant, which is the denominator of most of the report. Candidates are a naming convention, the EDRMS Site Type term, or an AvePoint provisioning flag.
  3. Where does the site to department mapping come from? AvePoint may already hold it from provisioning. If not it has to be created, and it is a records decision rather than a technical one.
  4. Can FileSizeBytes be added to FileMeta? Needed only for per record storage. Library and format storage can come from the inventory scan without it.
  5. Who owns and runs the inventory scan? It needs an identity with tenant wide read. Search and Graph are security trimmed, so an identity that cannot see every site returns quietly low numbers rather than an error.
  6. Which storage definition does the report mean? Site storage from M365 includes version history and the recycle bin, so it will not match the sum of current file sizes, often by several times. Both are legitimate. The dashboard must say which one it shows.
  7. Do all retention labels mark items as records? If some do not, dim_retention_label.marks_as_record does real work and every count must filter on it.
  8. What happens to disposed records? If they leave the counts, historical trends change retrospectively. Soft delete via IsDeleted already gives the option to keep them, which is the safer default.
